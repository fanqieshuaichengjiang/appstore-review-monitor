# 应用市场审核结果巡检 · App Store Review Monitor

不登开发者后台，只抓各应用市场**公开详情页**的最新版本号 / 构建号 / 更新日期，
按两条硬条件告诉你：这次发版，**哪些商店已经上线、哪些还在审核中**。

> 适用场景：App 提审后，想知道国内十几家应用商店各自什么时候放量。
> 挨个去商店搜、看版本号太费事，这个工具把它变成一张表。

- **纯标准库**：只用 `urllib` + `http.server`，不需要 `pip install` 任何东西。
- **配置驱动**：想巡检哪些商店、按什么顺序显示，全写在 `config.json` 里，
  也能在一个本地网页上点点改改，不用手编 JSON。
- **不碰开发者后台**：只读公开页面，不做任何写操作。

```
appstore-review-monitor/
├── check_review_status.exe  # ★ 目标机器没有 Python 时，双击这个
├── check_review_status.py   # 入口：抓取 + 判定 + 出报告（纯标准库）
├── webui.py                 # 本地网页服务：结果页 + 设置面板 + 日志
├── config.json              # 唯一的配置文件（应用信息 / 渠道清单 / 发版基线）
├── check_review_status.spec # PyInstaller 打包配方
├── 用手机看结果.bat           # 想让自己的手机也看结果时，双击这个
├── 使用说明.txt              # 给非技术使用者看的简明说明
├── README.md / LICENSE / .gitignore
├── history/                 # 每次巡检的快照（latest.json + 按日期留档）
├── backup/                  # 保存配置前的自动备份（改错了从这里找回）
├── logs/                    # 服务日志 server_<日期>.log（自动清 30 天前的）
└── report/                  # 每次巡检的 Markdown + HTML 报告
```

> `history/` `backup/` `logs/` `report/` 都是运行时自动生成的，**首次运行会自动创建**，
> 不需要手动建目录。`config.json` 同样会在首次运行时自动生成一份带示例值的
> ——生成之后**先别急着让它跑**：首次启动会直接把设置弹窗摊开引导你填，
> 填完点「保存并重新巡检」才开始第一次抓取。
>
> ⚠️ 仓库里那份 `check_review_status.exe` 是**打包那一刻的代码快照**。
> 改了 `.py` 之后必须**重新打包**，否则双击跑的还是旧逻辑（见下「打包」一节）。

## 快速开始

### 前置要求

**Python 3.9+**（开发时用的是 3.13）。没有第三方依赖，装好 Python 就能跑。

### 1. 填配置

**第一次启动不会去抓，而是直接把「设置」弹窗摊开、上面顶一条绿色引导** ——
因为这时程序还不知道你要巡检哪个应用，拿模板里的示例信息去抓，15 家商场
只会全部回「查无此应用」，白等几分钟还看得一头雾水。

填完点右下角 **「保存并重新巡检」**，第一次抓取就开始了；之后再打开就是正常
「启动 → 后台自动抓一遍」的流程，不用再管设置。

`config.json` 会在第一次运行时**自动生成**（示例值），你也可以先手动复制一份改。
最少要填这几项：

```json
{
  "app_name": "你的应用名",
  "android_pkg": "com.yourcompany.yourapp",
  "ios_track_id": 1234567890,
  "release_date": "2026-10-01",
  "channels": [ ... ]
}
```

- `app_name`：拿去各商店**搜索**用的名字，也显示在报告标题上。
- `android_pkg`：安卓包名。绝大多数安卓市场靠它定位。
- `ios_track_id`：App Store 的 trackId（纯数字）。只发安卓就留 `null`。
- `release_date`：本次提审 / 计划发布日期，**日期阈值法的分界点**。
- `channels`：要巡检哪些商店、按什么顺序显示（见下节）。

### 2. 运行

```bash
python check_review_status.py
```

会自动起一个本地网页服务并打开浏览器到 `http://127.0.0.1:8765/report`。
页面上就能看结果、改配置。第一次会用引导页取代结果表（见上一步）。

只想跑一次、在控制台看表格：

```bash
python check_review_status.py --cli
```

跑完生成 `report/review_status_<日期>.md` 与 `.html`，然后退出。

### 3. （可选）打包成 exe

仓库里已经带了一份打好的 `check_review_status.exe`，目标机器没有 Python 时双击即可。
但**它只是打包那一刻的代码快照**——你改了 `.py` 之后，必须重新打包才能生效：

| 你改了什么 | 要不要重新打包 |
|---|---|
| `config.json`（应用信息、渠道清单、发版基线…） | **不用**，exe 每次运行都会重新读它 |
| `check_review_status.py`（抓取 / 解析逻辑、新增渠道…） | **要重新打包** |
| `webui.py`（网页界面、校验规则…） | **要重新打包** |

```bash
python -m venv .venv
.venv\Scripts\pip install pyinstaller
.venv\Scripts\pyinstaller --noconfirm --clean check_review_status.spec
```

产物在 `dist/check_review_status.exe`，**拷到项目根目录覆盖旧的那个**
（必须和 `config.json` 放在一起）即可。

> 判断手上的 exe 是否落后：比一下 `.py` 和 exe 的**修改时间**。
> `--onefile` 的 exe 每次启动会先解压到临时目录，**首次启动慢几秒**属正常。
> 打包机与运行机都要求 Windows x64；换平台（如 ARM 本）需要重新打包。

## 配置：`config.json`

### 顶层字段

| 字段 | 说明 |
|---|---|
| `app_name` | 应用名。用于在商店里搜索，也显示在报告标题。 |
| `android_pkg` | 安卓包名。多数安卓市场靠它定位。 |
| `ios_track_id` | App Store trackId（纯数字）。不用 iOS 就留 `null`。 |
| `ios_bundle_id` | iOS bundleId。留档用，可留空。 |
| `release_date` | 本次提审 / 计划发布日期（`YYYY-MM-DD`）。**必填**。 |
| `target_version` | 本次发版的对外版本名（如 `1.2.3`）。不知道就留 `null`。 |
| `target_codes` | 本次发版的**构建号**，按「端」分别填。不知道就留 `null`。 |
| `channels` | 渠道清单（见下）。 |
| `app_ids` | 少数市场需要的额外 ID（见下）。 |
| `manual_reference` | 人工登记表：抓不到时用来兜底（见下）。 |
| `notify` | 消息通知：把结果推到群机器人（见下）。不想用就保持 `"on": false`。 |
| `timeout` | 单个请求超时秒数，默认 25。 |

以 `_说明_` 开头的字段是**写给你看的注释**，程序会忽略，随便删。

### `channels`：要巡检哪些商店、按什么顺序

**数组顺序就是报告里的行顺序**。每项：

```json
{
  "key": "小米",
  "name": "小米应用商店",
  "platform": "安卓",
  "fetcher": "xiaomi",
  "enabled": true
}
```

| 键 | 必填 | 说明 |
|---|---|---|
| `key` | ✅ | 渠道的**唯一标识**，也用作人工登记表的键。改了就相当于换了一家。 |
| `name` | ✅ | 显示名，出现在报告表格里。 |
| `platform` | ✅ | 这一家属于哪个「端」：`安卓` / `苹果` / `鸿蒙`（也可以自定义别的名字）。决定它跟 `target_codes` 里的哪个构建号比。 |
| `fetcher` | ✅ | 抓取器名字，对应代码里 `FETCHERS` 表的一个键。**留 `null` = 这家只能人工核验**（没有可自动抓取的公开数据源）。 |
| `enabled` | | `false` 则不抓也不显示。默认 `true`。 |
| `report` | | `false` 则照抓但不进报告（用来做交叉参考）。默认 `true`。 |
| `search_name` | | 这家商店上的**登记名**（和 `app_name` 不一样时才填）。不填也能跑：搜到结果后是**双向包含**匹配 + **包名校验**，见下。 |
| `note` | | 说明文字，抓不到时显示给操作者看（例如「该市场没有公开数据源」）。 |

**关于「鸿蒙只能人工」的刻意设计**：鸿蒙因为没有独立的公开数据源，
默认配置里 `"fetcher": null`——它**不会发任何请求**，只走人工登记表。
由此带来一个附带好处：设置页里的「构建号」输入框只列出**真的有抓取器的端**
（默认就是「安卓 / 苹果」），所以**鸿蒙不需要填构建号**。

**关于「Google Play 默认是关着的」**：默认配置里的 `谷歌` 这条带 `"enabled": false`。
原因是 Google Play 对**没上架的包名会返回 404**，而在本工具里那等于
「服务端明确答复查无此应用」→ 报告会显示 **⛔ 已下架**。
如果你本来就没在 Google Play 上架，开着它只会让报告里凭空多一行红字。
**确实上架了就把勾选框打上**：它用 `android_pkg` 定位（不需要额外填 ID），
`platform` 也是 `安卓`，所以**不会多出一个构建号输入框**。

**关于「商店里的登记名和你的应用名不一样」**：这很常见——你在设置里填「夸克浏览器」，
百度手机助手里它登记的却只有两个字「夸克」。所以名字匹配是**双向**的
（`_name_hit()`：`q in s` 或 `s in q`，任意一边包含另一边都算候选），
**不是**只判「返回的名字里包含你填的名字」。否则短登记名会被全部挡掉，
应用明明在架却被判成「抓取失败」。

> 放宽名字这一步**不会**带来误判：候选最终都要过**包名校验**
> （详情接口返回的 `package` 必须等于 `android_pkg`），名字只负责把明显无关的结果挡掉。
> 只有当你的应用名在商店里被改得**面目全非**（既不被包含也不包含登记名）时，
> 才需要在 `search_name` 里写上那家商店的实际登记名。

### `app_ids`：少数市场需要的额外 ID

多数安卓市场靠 `android_pkg` 就能定位，不需要在这里填。需要的几家：

| 键（=渠道 `key`） | 填什么 | 找不到怎么办 |
|---|---|---|
| `华为` | AppGallery 详情页 URL 末尾的 `C` 编号 | 不填会直接报错（不能猜） |
| `OPPO` | 详情页 URL 里的 `app_id`（纯数字） | 不填会直接报错 |
| `VIVO` | vivo appId | 不填则按 `app_name` / `search_name` 去搜 |
| `360应用` | 360 详情页的 `sid` | 搜索接口不稳，建议填上兜底 |
| `百度` | docid | 可留空；搜索搜不到时才用到 |
| `搜狗应用` | docid | **必填**，不填就别启用这家 |

设置面板会给每个填了 `fetcher` 的渠道自动生成一个输入框，
百度还会多一个配套的 `百度pid`。

> `谷歌` 在设置页里也有一个输入框，但提示语是**「不需要在此填写」**——
> 它靠 `android_pkg` 定位。`苹果` / `谷歌` 都属于「有抓取器但不用额外 ID」的情况。

### `manual_reference`：人工登记表

**会参与报告生成**，是抓不到公开数据的渠道的兜底来源。可用值：

| 值 | 含义 |
|---|---|
| `未发版` | 该渠道本次**没有上传包提审**：报告直接显示「未发版」，并且**跳过**对它的抓取。 |
| `已下架` | 该市场里已经没有这个应用了（适合给「只能人工」的渠道手工标注）。 |
| `审核中` / `审核通过` / `审核未通过` | 抓不到公开数据时用这里的结果补进报告。 |

规则：
- 登记为 `未发版` 的渠道，**不会去抓公开页**（公开页上挂的是旧版本，数据不适用）。
- 其余值**只在自动抓取失败时生效**；自动抓到了就以公开数据为准。
- ⚠️ **例外**：自动抓取如果拿到「服务端明确答复查无此应用」，会判 **已下架**，
  并且**压过**这里的登记值（登记原文会写进报告的说明里，不丢信息）。

## 网页界面：看结果 + 改配置

| 页面上的东西 | 做什么 |
|---|---|
| 右上角 **⚙ 设置** | 弹窗改：应用信息 / 发版基线 / 渠道与排序 / 人工登记表 / 各市场应用 ID / 消息通知 |
| 右上角 **↻ 重新巡检** | 立刻重新抓一遍，跑完自动刷新 |
| 弹窗里 **仅保存** | 只写配置，然后用**上次抓到的数据 + 新配置**重判一遍（秒出结果，不重新抓） |
| 弹窗里 **保存并重新巡检** | 保存后顺手重新抓一遍 |

设置面板里的渠道表：**勾选框决定显示哪些，↑↓ 箭头决定先后顺序**——
所见即所得，改完保存即可，不用碰 JSON。

几个刻意的设计（不是随手定的）：

- **默认只监听 `127.0.0.1`**。默认不对外开放，所以也没做账号密码——外人根本连不上。
- **先校验再落盘**：日期必须是合法「年-月-日」、构建号必须是纯数字、
  包名要像包名、渠道的 `fetcher` 必须真实存在、至少要留一家启用。
  任一项不合法就**整条拒绝**，把原因显示在弹窗顶上，绝不写半对不对的值。
- **保存前自动备份**到 `backup/config_<时间>.json`（保留最近 30 份），
  写入用「先写临时文件再 `os.replace()`」的**原子写**，不会出现写一半的坏文件。
- **并发保存不会互相覆盖**：保存全程加锁并带「配置指纹」校验——若你打开弹窗之后
  别人改过，会明确提示「请关掉设置窗口重新打开」，而不是静默覆盖，也不静默丢。
- **真 patch 语义**：`POST /api/config` 只处理 body 里真的带了的键，
  没带的保持原样，不会被清空。
- **`/report` 每次现渲染** + `Cache-Control: no-store`——改完配置刷新立刻生效。
- 页面用**上次快照 + 当前配置**重算，所以服务刚启动就有内容，不用干等全量抓取。
- **每次改动都写日志**（`logs/server_<日期>.log`），记了来源 IP 与改前改后的值。
- **`/healthz`**：极简存活探针，只回 JSON。

### 用自己手机看结果

默认只监听本机。想让**自己的手机**看，双击 **`用手机看结果.bat`**，
它等价于：

```bat
python check_review_status.py --lan --browser --port 8765
```

启动后黑窗口会打印一行形如 `http://192.168.1.23:8765/report` 的手机地址，
手机连同一 WiFi 打开即可。第一次可能弹防火墙提示，**勾上「专用网络」和「公用网络」
再点「允许访问」**。

> ⚠️ 开了 `--lan` 之后，**同一 WiFi 下任何人都能打开页面并改配置**（没有密码），
> 别在公司 / 公共 WiFi 下用。只想自己在电脑上看，就直接 `python check_review_status.py`。

## 消息通知（可选）：把结果推到群里

不想每次都去开网页，可以让它**巡检完自己把结果推到群里**。支持三种群机器人：

| `type` | 平台 | 去哪拿 webhook 地址 |
|---|---|---|
| `wecom` | 企业微信群机器人 | 群 → 右上角「…」→ 群机器人 → 添加机器人 → 复制 Webhook 地址 |
| `feishu` | 飞书群机器人 | 群 → 设置 → 群机器人 → 添加机器人 → 复制 Webhook 地址 |
| `dingtalk` | 钉钉群机器人 | 群 → 群设置 → 智能群助手 → 添加机器人 → 自定义 → 复制 Webhook |

在网页「⚙ 设置 → ⑥ 消息通知」里配，**不用手写 JSON**：

- **通知开关**：关着就完全不发（下面填的地址只是先存着）。
- **推送时机**：
  - `每次都发`（`always`）——适合发版后手动跑一次；
  - `只在有变化时才发`（`change`）——适合每天定时跑，只推「相比上次有变化」的，
    正文里会多一段 `🔁 小米：审核中 → 已上线`。
    - ⚠️ **第一次跑（还没有上次结果可比）时它不会推送**——没有基准就谈不上「变化」。
      想让第一次也收到，先切成 `每次都发` 跑一次建好基线，再切回来。
    - 它比的是 `history/latest.json` 里的上一次结果（状态级别），**不是**公开版本号；
      也就是说「版本号从 4.7.6 涨到 4.7.7 但仍未过审」不会触发推送，
      「审核中 → 已上线」才会。
- **群机器人列表**：一行一个，选类型、粘地址，可以点「+ 添加一个机器人」加行、
  点「移除」删行。**Webhook 留空的行会被自动忽略**，所以可以留几行空着备用。
- **发一条测试消息**：填完点这个按钮，当场验证地址填对没有。它走的是和正式推送
  **完全同一条**代码路径（同一个 `send_notifications(..., testing=True)`），所以测试通过就等于正式推送也通。
  发出去的标题是 **`【测试】XX · 通知测试`**，和正式报告的 `XX · 各市场审核巡检`
  **一眼可分**——不然群里几条消息堆在一起，根本分不清哪条才是真结果。

落在 `config.json` 里长这样：

```json
"notify": {
  "on": true,
  "mode": "always",
  "providers": [
    { "type": "wecom", "name": "企微群", "webhook": "https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxx" }
  ]
}
```

推出去的内容（三家各自用合适的格式：企业微信 / 钉钉用 markdown，飞书用交互式卡片）：

```
【示例应用 · 各市场审核巡检】
巡检时间：2026-10-14 15:20

已上线 9 ｜ 审核中 3 ｜ 已下架 1

已上线（9 家）
✅ 苹果 ｜ 华为 ｜ 小米 ｜ OPPO ｜ VIVO ｜ 应用宝 ｜ 三星 ｜ 联想 ｜ 应用汇

需要关注（4 家）
⏳ 360应用（360 手机助手）：审核中 —— 公开 4.7.6 / 2026-09-01，未达发版基线
⛔ 百度（百度手机助手）：已下架 —— 服务端明确答复 HTTP 404
```

几个刻意的设计（不是随手定的）：

- **只发不读**：单向推送，不回读群消息。
- **已上线的也列出来，但只并列短名**：只给「已上线 9」一个数字的话，看不出是哪几家、
  没法跟同事核对；可逐条铺开又会让群消息长一倍，而它们本身没有待办含义。
  所以折中——已上线并成一行，**只有「需要关注」逐条列并带判据**。
  一行都上线时收尾会写「所有渠道均已上线。」。
- **打开页面不算「巡检」**：双击 exe 启动服务时，它会先在后台抓一遍好让页面立刻有内容
  ——这一次**不推送**（`run_scan(..., push=False)`）。否则「每天开一次网页看结果」
  就变成「每天群里多一条」。只有你主动点 **「↻ 重新巡检」** 或
  **「保存并重新巡检」** 时才推。命令行 `--cli` 是你自己跑的，照推。
  （⚠️ **还没填过应用信息的首次启动，连这一遍后台抓取都不做** ——
  见 `webui.needs_setup()`：只认「应用名 / 安卓包名是不是还停在模板值」，
  不看 `config.json` 存不存在。否则「打开看了一眼就关掉」的用户，
  下次启动会被当成"已配置"，然后拿示例应用去跑一遍全量抓取。）
- **推送失败绝不影响巡检**：报告已经落盘了，推送只是「顺手告诉群里一声」。
  发失败会在控制台、日志、报告页顶部各留一行「推送失败：XX（原因）」。
- **HTTP 200 ≠ 成功**：三家的 webhook 都是「HTTP 200 但 body 里带错误码」的套路
  （地址失效、被限流、内容超长都会这样），所以代码会再解析一次
  `errcode` / `code` / `StatusCode`，只有真为 0 才算成功。
- **类型会被域名纠正**：企业微信的地址被误选成「飞书」时，保存会**按域名自动改回 `wecom`**
  ——这种错几乎必然是下拉选错了，与其让消息发不出去、还得回来猜，不如直接纠正。
- **同一个地址填两遍会被拒**，免得群里收到双份。
- ⚠️ **webhook 地址等于「谁能往你群里发消息」**：别把 `config.json` 或开了 `--lan`
  的页面交给不信任的人。

## 判定逻辑（只认两条，命中任一即「已上线」）

1. **公开更新日期 ≥ 发版日期**（`release_date`）
2. **公开版本 == `target_version`**，或**公开构建号 == 该端在 `target_codes` 里的值**

未命中一律记为 **审核中**。此外还有几个特殊状态：

| 状态 | 什么时候出现 |
|---|---|
| **已上线** | 命中上面任一条 |
| **审核中** | 有公开数据，但两条都没命中 |
| **未发版** | 人工登记表里标了「未发版」（本次没传包） |
| **⛔ 已下架** | 数据源**正常通信后明确答复查无此应用** |
| **⚠️ 抓取失败** | 超时 / 非 200 / 解析不到 → 退人工登记表，报告底部单独点名 |

### 「已下架」与「抓取失败」是两件事

这两个状态**不能混**，代码里用一个专用异常 `DelistedError` 严格分开：

| 现象 | 性质 | 报告里 |
|---|---|---|
| 服务端**明确答复**资源不存在 | 可信的**否定结论** | ⛔ 已下架（来源 `自动`） |
| 超时 / 非 200 / 对方改版 / 解析不到字段 | **故障**，数据不可信 | ⚠️ 退人工登记表，底部点名 |

把「故障」当成「已下架」会误报业务问题；把「已下架」当成「故障」，
则会让一次真实的下架事件淹没在「接口又坏了」里。
所以**只有拿到服务端明确的 not-found 语义**时才判「已下架」，其它一律算故障。

### 报告里有什么

报告是一张表，列：**平台 | 市场 | 公开版本 | 更新时间 | 状态 | 数据来源**。
`数据来源` 只有两种：`自动`（本次抓的公开页）或 `人工`（取自登记表）。

最后两家是**结构性缺口**，不是没写好：

- **鸿蒙**：AppGallery 的公开网页接口只服务**安卓**内容。
  实测用华为自己的 C 编号去查，返回的 76 KB 响应里
  `harmony` / `ohos` / `hmos` / `hap` 命中为 **0**，唯一的包名是安卓包。
  已穷举 19 个参数变体、6 个 UA、6 个主机、16 个 `serviceType`，内容恒定。
  用**对照组**验证过（支付宝、钉钉都确有鸿蒙版，在同一接口里同样 0 命中）
  ⇒ 这是**接口能力边界**，不是某个 App 的特例。
  若哪天拿到鸿蒙**独立的 C 编号**，填进 `app_ids` 并把该渠道的
  `fetcher` 换回 `"huawei"` 即可恢复自动。
- **荣耀**：连一个可访问的公开详情页都没有。

> 默认配置里这两家 `fetcher` 是 `null`，走人工登记。
>
> **Google Play 是唯一「只能按日期判定」的渠道**：它的网页详情页不公开
> versionName / versionCode，所以 `target_codes` 里的安卓构建号对它不起作用，
> 报告里「公开版本」那一列会是空的——这不是抓错了，是它本来就只公开更新日期。
> 另外包名不存在时它返回 **HTTP 404**，会被判成「⛔ 已下架」（详见上面那节）。

## 怎么加一个新渠道

加一家新商店需要**改两个文件、动三处**。以加「XX 应用商店」为例：

### 第 1 步：写一个抓取函数

在 `check_review_status.py` 的抓取器区域加一个 `fetch_xxx(cfg)`：

```python
def fetch_xx(cfg):
    """XX 应用商店：https://example.com/app/<包名>

    这里写清楚：数据源 URL、你是怎么发现的、返回的长什么样、
    有哪些坑。半年后回来看会感谢自己。
    """
    pkg = cfg["android_pkg"]                      # 或 cfg["ios_track_id"]
    url = f"https://example.com/app/{pkg}"
    t, tag = http_get_fresh(url, required=r'"versionName"',
                            timeout=cfg["timeout"])
    d = json.loads(t)
    ver = norm_ver(d.get("versionName"))
    if not ver:
        raise RuntimeError("XX 商店未解析到版本号")
    return {
        "version": ver,                    # 公开版本名
        "code":    str(d.get("versionCode") or ""),   # 公开构建号（可选）
        "date":    norm_date(d.get("updateTime")),    # 更新日期
        "url":     url,                    # 详情页链接（写进报告）
        "note":    "版本名 / 更新时间",      # 抓到的字段说明
        "fetch_tag": tag,                  # 数据来源标记（"源站直取" / "CDN 缓存"）
    }
```

**契约**（所有 `fetch_*` 都一样）：

| 项 | 说明 |
|---|---|
| 入参 | 只收一个 `cfg`（整个配置 dict）。要用的东西从里面取：`cfg["android_pkg"]`、`cfg["ios_track_id"]`、`cfg["timeout"]`；要额外 ID 用 `app_id_of(cfg)`（会正确解析出本渠道在 `app_ids` 里登记的值，主流程已注入渠道上下文）。 |
| 返回 | 一个 dict，键见上面示例。`version` / `date` 至少要有一个有值。`code` 是公开构建号，没有就不给。 |
| 搜索名 | 需要按名字搜的，用 `search_name_of(cfg)`（会优先取渠道自己的 `search_name`，否则用全局 `app_name`）。 |
| 出错 | 普通故障（超时/改版/解析不到）→ `raise RuntimeError("说人话的报错")`。 |
| 已下架 | **只有**拿到服务端明确 not-found 语义时 → `raise DelistedError("...")`。**不要**在「搜不到」时就抛。 |

**手边可用的工具**（都在同一个文件里，直接调）：

- `http_get_fresh(url, required=..., headers=..., timeout=...)` — **带防缓存参数**的请求，
  返回 `(正文, 来源标记)`。**务必用它**，别直接用 `urllib`：

  > ⚠️ **首坑：CDN 旧缓存会让「已过审」看成「还在审核中」。**
  > 源站已经发布新版本、边缘节点还挂着旧页面时，裸请求会拿到过期数据——
  > **HTTP 200、字段齐全、不报错**，只是版本号和日期都是上一版的。
  > 这属于最坏的静默错误。
  >
  > `http_get_fresh` 先带 `?_t=<毫秒时间戳>`（命中全新缓存键 → 回源）请求，
  > 若返回正常但 `required` 正则不匹配（说明该站对多余参数敏感），自动退回裸地址重试。

- `norm_ver(v)` — 版本号归一化（`v1.2.3` → `1.2.3`）。
- `norm_date(s)` — 把 `2026.9.16` / `2026年9月16日` / `2026-09-16` / 毫秒时间戳统一成 `YYYY-MM-DD`。
- `_pick(node, patterns)` / `_norm_key(s)` — 在 JSON 里按字段名「模糊匹配」取值。
  **键名会先归一化**（转小写、去掉 `_` `-` 空格），所以
  `versionName` / `version_name` / `VERSION-NAME` 是同一条 pattern。
  ⚠️ 注意 pattern 里**不要带 `_`**——归一化后 `_` 已经没了。
  （踩过的坑：360 的接口是蛇形键 `version_name` / `version_code`，
  pattern 写 `^version` 会先命中 `version_code`。）
- `first(pattern, text, group=1)` — 正则取第一个匹配。

### 第 2 步：注册到 `FETCHERS`

```python
FETCHERS = {
    ...
    "xx": fetch_xx,     # ← 加这一行
}
```

顺手在 `FETCHER_ID_HINT` 里加一行（会被设置页当成输入框提示文案）：

```python
FETCHER_ID_HINT = {
    ...
    "xx": "应用包名",     # 或 "详情页 URL 里的 xxx（纯数字）"
}
```

### 第 3 步：在 `config.json` 的 `channels` 里加一条

```json
{ "key": "XX商店", "name": "XX 应用商店", "platform": "安卓", "fetcher": "xx", "enabled": true }
```

**放进数组的哪个位置，它就显示在报告的第几行。**

搞定。**不需要**改判定逻辑、报告渲染、网页界面——那些都是配置驱动的。

### 加完之后

- 想知道这台机器能不能抓通，先跑一次体检（**几秒**，不写报告）：
  ```bash
  python check_review_status.py --preflight
  ```
- **改完要跑一次全量**，不要只单测新渠道——新旧渠道之间可能有你没预料到的相互影响。
- ⚠️ 若你用的是打包好的 exe：**改了 `.py` 必须重新打包**，否则双击跑的还是旧逻辑。

## 命令行参数

| 参数 | 作用 |
|---|---|
| （无） | 起本地网页服务并打开浏览器（默认行为） |
| `--cli` | 不启服务，只跑一次巡检、控制台出表格 |
| `--preflight` | **连通性体检**：并发试一遍所有渠道，几秒回答「这台机器能不能抓通」，不生成报告、不写 `history/` |
| `--port 8765` | 换端口；默认 8765，被占用会自动往后顺延 |
| `--lan` | （= `--host 0.0.0.0`）开放给同网段访问，启动时打印手机能打开的地址 |
| `--browser` | 配合 `--lan` 用：`--lan` 默认**不**自动开浏览器，加上它本机也会打开 |
| `--no-scan` | 启动时不巡检，先看上次结果（快，适合只想改配置时） |
| `--no-browser` | 不自动打开浏览器（没有桌面会话的环境用得上） |
| `--show-raw` | 打印原始抓取片段（排障用） |
| `--host <addr>` / `--strict-port` | 指定绑定地址 / 端口被占不顺延 |
| `--no-pause` | （exe 模式）跑完不停顿直接退出 |

## 注意事项

- 本工具**只读公开页面**，不会对任何渠道做写操作。
- 请求带防缓存参数，每次都会回源、不命中 CDN。一天跑一两次无所谓；
  **若要高频轮询（比如几分钟一次），请留意别把源站请求量堆上去。**
- **「公开更新日期」≠「版本发布日期」**，推断结论不等同于开发者后台的官方审核状态；
  标 `人工` 来源的渠道请以开发者后台为准。
- 各市场页面 / 接口若改版，对应解析规则需同步调整——
  都集中在 `check_review_status.py` 的 `fetch_*` 函数里，**一个渠道一个函数，互不影响**。
- **网页服务默认只监听本机，且没有登录鉴权**（因为默认只有本机能访问，不需要）。
  用 `--lan` 时同网段任何人都能打开并改配置，注意场合。
- 服务本身没有 HTTPS。`config.json` 里的应用 ID 若属内部信息，
  **不要把它放到公网服务器上裸跑。**
